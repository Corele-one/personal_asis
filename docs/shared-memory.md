# 共享记忆：M1 合成权威服务

## 当前取舍（2026-11-10）

按本轮委托，当前选择**共用资料能力优先，暂缓Mem0上线**。Mem0继续停用，已有代码、合成数据和验收作为备选保留；M2／W3不作为近期其他功能的前置，也不为了本试点单独升级机器。不是将自动跨会话记忆标为已由资料工具替代。

当日只读复核：当前机器为Google Compute Engine `e2-micro`，官方规格1GB，系统可见物理内存964.56MiB；另有1024MiB swap。Mem0停用时，本次瞬时可用268.33MiB、swap已用724.05MiB，说明余量问题是整机共存问题。规格见[Google官方表](https://docs.cloud.google.com/compute/docs/general-purpose-machines#e2_shared-core)，实际观测与容量规格分开理解。

Mem0的独立SDK试验进程峰值约138–147MiB，完整接口的采样物理占用最高约160MiB；这些是本项目的少量合成负载测量，不是官方统一内存要求。整机swap峰值约880MiB不能归给Mem0；验收额外SDK进程自身约186–188MiB，也使本轮不足以判断正常自然使用时的增量压力。当前不依据这次短测宣称Mem0一定不能运行或必须扩容。

资料工具处理“找原文、读来源、按日期复盘”；个人记忆处理“哪条偏好／决定当前有效，如何被修订或撤回”。当前接受后者的自动化暂缓，继续使用各端自己的会话和已有获准背景；不新造另一套自动记忆引擎。若后续需要共享精选背景，复用原有来源与具体预览确认规则，不能自动把旧背景变成Work的当前画像或新增发布。

未来仅在稳定偏好／决定的跨端不一致成为主要使用问题，且容量余量／代表性长测已具备时恢复评估。恢复后仍保持一份有效个人记忆的权威，多端只是客户端；具体引擎可以复评，不绑定必须永远使用Mem0，也不让各端各自维护互相冲突的个人画像。当前优先改善W2自然使用、资料覆盖／新鲜度和Chat／Work本身的质量。

## 结构和数据边界

- 一个独立 `asis-memory` 身份／`personal-asis-memory.service`，固定 Mem0 OSS `2.2.1`；Python `3.12.14` 和既有依赖复制到 root 管理的独立运行目录，不修改 AstrBot 环境或开放其私有目录。
- SDK负责向量、记忆正文、检索、更新和历史；Qdrant local 与 SQLite history 均在私密持久盘，由唯一进程持有。没有 PostgreSQL、图数据库、本地模型或另一个主 Agent。
- 候选筛选只处理必要本人原话，使用既有 VPS MiMo `mimo-v2.6-flash`，显式关闭 thinking、使用 JSON 输出；依据[官方参数](https://mimo.mi.com/docs/api/text-generation/openai-api)及[结构化输出](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/text-generation/structured-output)。经校验的偏好／决定通过 `infer=False` 保存，禁止 SDK 再做第二次泛化抽取。
- embedding 复用既有 VPS Google 的 `gemini-embedding-001`、768维。抽取和向量均无自动重试，发出前在独立调用账本占位；`infer=False` 仍会调用 embedding。M1试验账本限定32次抽取／100次向量请求，未提高旧系统预算。
- 正式个人内容尚未初始化；当前 collection 为 `m1_synthetic`，不能直接把它当作正式个人记忆。M2须另建干净正式空间并核对迁入内容，不能混入合成人物和偏好。

SDK及模型、向量数据流均已明确配置，不依赖默认 OpenAI 账号。原生 Alma 个人记忆与主动 Check in 仍关闭。遥测关闭，服务不输出正文、凭据或上游错误原文；只记录固定启动失败类别。

## 身份、版本和失败语义

接口仅绑定 `127.0.0.1:23101`，不公开代理。每个验收客户端持有独立 Bearer Token；服务端固定同一合成本人身份，客户端／会话只作为出处，模型不能传入任意 `user_id`。按 ID 查询、历史、修改和撤回都校验归属。当前验收凭据没有提供给 Alma 或 AstrBot，正式接入时分别发布客户端配置。

`POST /v1/memory` 接收 `action` 和 `arguments`。首批接口为 `status/list/get/search/capture/history/validate/withdraw`；`preview` 仅供验收管理员验证合成抽取。所有保存／撤回要求 `synthetic=true`。状态分别报告存储、版本一致性、个人内容初始化、自动保存及客户端接入，进程在线不冒称个人记忆可用。

- 临时要求、引用、AI建议和生活事件不成为稳定偏好；取消保留取消身份，同名不同项目分别保留范围。原话逐字片段、来源标识、取得时间和来源哈希可追溯。
- 明确纠正绑定目标和预期版本；两个客户端使用同一旧版本时，只允许一个成功。已有同范围／主题的记录不通过相似度机械覆盖，要求明确纠正目标。
- 来源重复只返回已知结果，不再次调用模型或 embedding。请求发出后失败／结果未知，来源收据会阻止自动重发；通过 SDK metadata 只读核对已落盘结果后恢复。
- SDK与业务收据不是跨库原子事务。已验证新增／更新在SDK成功、收据未完成后的恢复；多候选只完成一部分等无法完整核对的情况保持不一致／未知，不返回旧事实或声称全部保存成功。缺失内容不能靠自动重跑生成补齐，需显式核对／修复。
- 客户端不缓存正文；有缓存的后续入口必须先 `validate(memory_id, version)`。修订／撤回立即改变 epoch，不能等 TTL 过期才停止使用旧版本。
- SDK history保留修订；回执库只保存标识、版本、来源定位和哈希，不存第二份记忆正文。原始聊天与已有批准背景不会被本服务改写。

## 撤回和备份恢复

撤回先持久化版本／来源阻断标记，再通过 SDK 删除当前记忆。核对固定版本后发现 SDK 的 delete 仍保留 history 旧正文，因此适配器还对已验证的 SDK history schema 做按 ID 清理并读回核对。当前接口不再返回旧正文，同一来源的再次送达也不能重新生成该记忆；`infer=False` 路径没有另存对话消息缓存，已实测核对。

删除范围是当前逻辑索引、SDK history及本接口缓存；这不等于磁盘取证级擦除，也不删除原聊天、平台、离线副本或旧备份。旧备份包含旧正文，保留范围必须分别处理。

`deploy/memory-checkpoint.py` 只在记忆服务停止、独占存储持有锁后复制同一检查点的 engine 和版本／撤回收据；凭据与计费账本不纳入回退。恢复前保留当前 engine，不用旧备份覆盖最新版本屏障和调用账本。恢复旧备份后：

1. 已撤回记录会再次从恢复的索引／history清理，不会重新出现。
2. 缺少当前有效修订的备份会令 `consistency_ready=false`，拒绝读取；只有恢复当前检查点或显式修复后再开放。
3. 新主机没有可核对的最新版本屏障时，工具拒绝自行从任意旧备份启动，需先提供已核对的最新屏障。

M1已实际演练旧版本拒绝读取、当前版本恢复和撤回后恢复旧备份。备份、恢复前保留的 engine 副本及合成验收目录均为私密数据；本轮未设置自动备份、自动清理或新的定时任务。首批保留期为7天，之后由维护时按检查点明确清理；未执行的清理不视为已删除。M2上线前补正式维护安排及个人备份撤回说明。

## 运行与回退

| 项目 | 位置／设置 |
|---|---|
| 程序／Python | `/opt/personal-asis-memory/current`、`venv`、`runtime`，root所有 |
| 数据 | `/var/lib/personal-asis-memory`，0700；私密文件0600 |
| 当前SDK空间 | `engine/qdrant`、`engine/history.sqlite3`、`engine/sdk` |
| 版本／撤回屏障 | `barriers.sqlite3`，不被旧备份自动覆盖 |
| 调用账本 | `calls.sqlite3`，不回滚已发出／未知请求 |
| 窄私密配置 | `config.json`，只含既有两提供商必要凭据和验收客户端 Token |
| 限额 | 高水位160MiB，最大192MiB，swap128MiB，CPU40%，不提高Work／Chat限额 |

停止／启动仅操作 `personal-asis-memory`；Chat、Work、只读资料接口和看板独立。停服务保留全部数据，不重放历史或未知请求。代码／服务回退由安装器的日期化 `/var/backups/personal-asis-memory/` 清单管理，不恢复旧资料库、屏障或消费记录。

完整检查点：在 VPS 以管理员运行 `python3 /opt/personal-asis-memory/current/deploy/memory-checkpoint.py backup`。恢复需显式 `restore --checkpoint <已核对目录>`，先理解上述旧版本拒绝读取行为。验收脚本每一步持久记录已发出／通过／未知；再次运行不会自动重发失败或未知的模型请求。

资源观察覆盖约15分钟／170次采样，含计划停启、恢复、实际SDK和Chat／Work串行轻任务；不是连续单进程15分钟存活或全天验收。未观测OOM或Work健康失败，但最低可用内存约116MiB，整机swap最高约880MiB，Work swap达到128MiB上限，Mem0 swap最高约107MiB；内存PSI full avg10最高13.52%。因此本轮未签收常驻资源门槛，已停止并禁用合成服务，不进入个人内容导入／自动保存。

SDK验收客户端自身另占约186–188MiB，部分压力峰值处于计划停启／导入阶段；这不是同负载开关Mem0的受控A/B实验，不能断言这些压力全部由Mem0常驻造成，也不能据此证明正常Chat全天余量足够。若未来恢复记忆上线，先解决容量余量或在当前资源下完成更贴近自然使用的长测，保持Chat和Work原限额与资料权限，再决定是否签收M1及推进M2；当前主线按本页顶部取舍执行。
